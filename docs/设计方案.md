# Artifex 控制台 · 前端设计方案

## 0. 一句话

给 Artifex（通用 AI 内容生产平台）做企业用户用的正式前端控制台。
本期只做**应用与配方**——后端已完成的那部分。

后端仓库：`~/Work/wanyan/go/artifex-core`（独立仓库，前后端分离）。

## 1. 范围

### 做

| 页面 | 干什么 |
|---|---|
| 应用列表 | 看有哪些应用，建应用，改应用 |
| 应用配方列表 | 看这个应用下有哪些配方，从模板建配方，选一个用 |
| 编辑配方 | 改一份配方的资料获取、创作要求、评审设置 |
| 布局外壳 | 顶栏 + 左侧导航（其余导航项置灰） |

### 不做

生产任务与进度、成品预览与下载、应用概览页、自动化、
登录注册、宣传页、通知中心、删除应用/配方。

理由分两类：

- **后端没有接口**——生产任务列表、用户体系。
- **后端有接口但产品不提供**——删除（`DELETE` 是运维自测用的，交接说明写明"正式前端别放删除按钮"）。

## 2. 技术栈

| 层 | 选型 | 为什么 |
|---|---|---|
| UI 库 | React 19 | 指定 |
| 构建 | Vite 8 | 控制台是登录后才用的内部系统，不需要 SEO。Next.js 的服务端渲染在这里是纯负担 |
| 语言 | TypeScript 5 | |
| 组件库 | **Ant Design 6** | 表格、表单、校验开箱即用；其 Form 天然支持"服务端返回一批字段错误 → 批量标红"，正对上后端 422 的设计。**v6 原生支持 React 19**，不需要 `@ant-design/v5-patch-for-react-19` 补丁 |
| 图标 | @ant-design/icons 6 | antd 6 要求配套升到 6，两者必须同版本 |
| 路由 | React Router 7 | |
| 服务端数据 | TanStack Query 5 | 见 §5.3 |
| 测试 | Vitest 4 + Testing Library | 纯逻辑（错误解析、字段可见性、枚举映射）严格测；组件只测关键行为 |
| 拖拽排序 | dnd-kit | 只为「自定义内容结构」的段落排序，约 10KB |
| 包管理 | pnpm | 机器上已有，无需全局安装 |

版本核对于 2026-08-29：antd 6.6.2 · React 19.2.8 · Vite 8.2.2 · React Router 7.18.3 ·
TanStack Query 5.102.8 · Vitest 4.1.11。Vite 8 要求 Node `^20.19 || >=22.12`，
本机 22.22.2 满足。

**明确不用**：Umi / Ant Design Pro（本期 4 个页面，它带的布局系统、权限、i18n、mock 绝大部分用不上）、
protobuf 工具链（见 §5.1）、任何需要全局安装的工具（见 §8）。

## 3. 页面与路由

### 3.1 布局外壳

```
┌─────────────────────────────────────────────────┐
│ [AI] AI 内容生产平台        行业洞察内容中心 ▾   │  顶栏
├───────────────┬─────────────────────────────────┤
│ ◨ 应用名        │                                │
│ ───────────── │                                 │
│ ⌂ 应用概览 ○   │          页面内容                │  ● 可用
│ ⚗ 应用配方 ●   │                                 │  ○ 置灰「敬请期待」
│ ↻ 自动化   ○   │                                 │
│ ☰ 生产任务 ○   │                                 │
└───────────────┴─────────────────────────────────┘
```

四项导航只有「应用配方」可点。**「应用概览」也置灰**——那页的三个数字卡有两个
（进行中任务、待处理任务）和「最近生产任务」列表全部依赖生产数据，后端本期没有；
剩下能做的只有"已启用配方 N"一个数字，撑不起一页。进入应用直接落到「应用配方」。

顶栏**不放**通知铃铛和用户头像。没有用户体系，放点不开的假控件在演示时会穿帮。

### 3.2 路由表

```
/                                → 跳 /apps

/apps                            应用列表（卡片）
  └ 弹窗  创建应用
  └ 弹窗  编辑应用（改名 / 改说明）

/apps/:appId                     → 跳 /apps/:appId/recipes
/apps/:appId/recipes             应用配方（表格）
  └ 弹窗  选择系统配方（= 从模板新建配方）
/apps/:appId/recipes/:recipeId   编辑配方（左分段导航 + 右表单）

/apps/:appId/overview            置灰，不可达
/apps/:appId/automation          置灰，不可达
/apps/:appId/tasks               置灰，不可达
```

「选择系统配方」这一屏**两份原型都没画完整**，但它是必须的——后端规定配方只能从模板复制，
不支持从空白创建。

### 3.3 为将来留的口子

以后要加登录和宣传页，现在只做两件成本极低的事，不做实体页面：

1. **认证边界**：控制台页面外包一层门卫组件，现在直接放行。接真登录时只改这一个文件。
2. **路由前缀**：需要时用 Vite 的 `base` 配置一行把控制台整体挪到 `/console` 下。

不现在做登录页的理由：后端**完全没有用户体系**，登录方式（手机号/邮箱/SSO）、
登录态存法（JWT/Cookie）、要不要租户、权限粒度——四个问题都没答案，
而它们决定前端一大半写法。现在猜一套，等后端定了基本要推翻重写。

宣传页建议**以后单独开一个项目**：它面向没付钱的潜在客户、要 SEO、由市场随时改文案，
和控制台是两种东西。混在一起会逼整个项目上服务端渲染。

## 5. 与后端对接

### 5.1 类型从哪来

**手写 TypeScript 类型，`recipe.proto` 只当接口文档看，不进构建流程。**

不用 protobuf 代码生成的理由：只有 14 条路由，量不大；引入 `buf`/`protoc` 工具链后，
本机和 CI 都要装，出问题时排查门槛高。

**但 proto 不能照字面翻译**——见下条。

### 5.2 实调验证：文档与实际不符之处

2026-08-29 实际启动后端逐条调用（`go run ./cmd/server`，MySQL 在 docker `artifex-mysql`）。
**以下以实际为准**：

| 项 | 文档/proto 说 | 实际 |
|---|---|---|
| 端口 | `:8080` | **`:18080`**（`config.yaml` 的 `server.addr`） |
| `GET /v1/apps` | proto 是 `AppListItem{app{…}, recipeCount}` **嵌套** | **扁平**：`appId`/`name`/… 与 `recipeCount` 平铺同级 |
| `SystemRecipe` | proto 声明 `appType`、`appTypeName` | **不返回这两个字段** |
| CORS | 交接说明称"后端没配 CORS" | **代码已支持**，`cors_origins` 填源即开（默认 `[]` = 关） |

第二条最险：照 proto 字面写类型，整个应用列表页会取不到任何值。

**已验证与文档一致**：错误体格式、404/400 的 `code`+`field`、
**422 一次返回全部缺失字段**、按 `appType` 裁剪（图文配方确无
`durationSec`/`shotCount`/`slideCount`/`hostCount`）、
重名自动追加「（副本）」、草稿 PUT 缺必填项返回 200 且状态不变。

**响应里 custom 系列字段表现不一致**：`customTone: null` 是存在的 key，
`customSections` 整个 key 不出现。所以判断要分两类，见 §7.2。

### 5.3 数据获取与缓存失效

用 TanStack Query 管服务端数据。不手写 `useState + useEffect` 的具体理由：
**写操作要连带刷新多处**，手写容易漏，漏了就是"页面显示的和数据库不一致"。

失效规则集中定义：

| 操作 | 刷新什么 |
|---|---|
| 创建 / 编辑应用 | 应用列表、应用详情 |
| 从模板创建配方 | 配方列表 |
| 保存配方 | 配方详情、配方列表 |
| **转就绪** | 配方详情、配方列表、**应用详情** |
| 选中使用 | 应用详情、配方列表 |

加粗那条最容易漏：后端验收里有一条——**应用尚未选中配方时，它的第一份配方转就绪会被自动选中**。
不刷应用详情，"使用中"标记就是错的。

### 5.4 错误处理

`api/client.ts` 把后端错误体统一包成 `ApiError`（`status` / `code` / `field?` / `errors?`），
按下表分发：

| 情况 | 处理 |
|---|---|
| 422 带 `errors[]` | **不弹提示**，交表单批量标红 |
| 400 带 `field` | **不弹提示**，只标红那一个输入框 |
| 404 | 提示后退回上一层列表 |
| 409 | 弹提示（业务冲突，如想选中一份草稿配方） |
| 500 / 网络错误 | 弹「服务异常，请重试」，**不展示技术细节** |

前两行是关键：**能定位到输入框的错误绝不弹提示条**，否则用户同时看到飘过的黑框和一堆红字，
说的还是同一件事。

## 6. 原型与后端契约的差异

产品原型（产品经理提供的高保真可运行原型）早于后端定稿，按理想产品画的。
**冲突一律以后端契约为准**——服务端会校验，照原型做必然报错。

### 6.1 要改的

| 位置 | 原型 | 后端事实 | 处理 |
|---|---|---|---|
| 配方列表 | 状态「启用/停用」+【停用】按钮 | 只有 `draft`/`ready`；"在不在用"看应用的 `selectedRecipeId` | 改成**草稿 / 就绪 / 使用中**，删【停用】 |
| 编辑配方 · 质量评审 | 整页分数：最少来源数、各项通过线、权重、系统底线 | **全部系统管理，接口不返回**；只开放 `autoRevisionCount` | 只留「自动修改次数」+ 一句只读说明 |
| 编辑配方 · 触发与决策 | 一整段 | 触发规则系统管理，接口不返回 | **整段删** |
| 编辑配方 · 资料检索顶部 | 搜索源：百度/Google/腾讯新闻/小红书/抖音/企业知识库 | **无此能力**；`sourceMode` 说的是另一件事——用不用用户自己的资料 | 换成后端真实三选一：系统自动准备 / 用户资料优先 / 仅用户资料 |
| 创建应用 | 内容类型 5 个（含博客内容、邮件订阅） | 4 个：`article` / `video` / `audio` / `slides` | 按后端的 4 个，文案沿用原型风格 |
| 应用列表卡片 | 底部「最近任务 + 状态」 | `latestJob` 本期恒为空 | **删掉**（不是显示"—"占位） |
| 选择系统配方弹窗 | 列出图文/视频/音频/博客/邮件，不可用的标"敬请期待" | 服务端已按应用类型过滤，图文应用**只返回 3 个图文模板**且全部 `available: true` | 照实际返回渲染；`available: false` 的仍按"敬请期待"处理（逻辑保留） |
| 编辑配方顶部 | 「所有修改已保存」自动保存 | 只有全量 PUT | 换成明确的【保存】按钮 |
| 正文字数 | 下拉选区间「1800～2200字」 | `targetWordCount` 是单个整数 | 下拉预设 800/1200/2000/3000 +「自定义」填数字；选区间存中值 |
| 左侧导航 | 四项，只有「自动化」置灰 | 只有配方模块可用 | 只有「应用配方」可点，其余三项置灰 |
| 右上角 | 🔔 通知（带小红点）、用户头像 | 无用户体系 | 删掉 |
| 配方列表「来源」列 | 显示来自哪个系统配方 | 列表接口不返回 `systemRecipeId` | 删掉该列 |

### 6.2 原样保留的

整体视觉（配色、圆角、字号、卡片风格）、应用列表的卡片形态、配方列表的表格形态、
编辑配方的"左分段导航 + 右表单"结构、指定/排除来源的标签输入、
检索轮数的 1/2/3 分段按钮、系统配方卡片上的 `features` 勾选项。

这些后端都对得上，照做。

### 6.3 两份原型不一致处

仓库里 `artifex-core/docs/prototype/` 那份把配方列表画成**卡片**，
产品经理那份画成**表格**。**取表格**——列表接口只返回名称/说明/状态/更新时间，
卡片会显得空，表格刚好装得下，配方多了也不乱。

## 7. 编辑配方表单（本期工作量最大的一页）

三个硬要求互相纠缠：字段按类型裁剪、保存与转就绪校验强度不同、全量提交。

### 7.1 四段共用一个表单

原型是"左分段导航 + 右表单"，看起来像四个独立页面，
**但它们是同一份数据的四个视图**——保存时一次性全量提交。

所以：**一个 `<Form>` 包住全部四段，分段导航只切换显示哪一块。**

好处很具体：转就绪失败时后端可能同时返回「资料检索」和「内容生成」两段的错误。
一个表单的话，`form.setFields()` 一次就把所有字段标红了，**包括当前没显示的段**。
再在左侧分段导航上标红点——哪段有问题一眼看到，用户不用一段段翻。
原型里「✓ 已完成」那个位置正好放。

四段：**基本信息 / 资料检索 / 内容生成 / 质量评审**（「触发与决策」已删，见 §6.1）。

### 7.2 字段裁剪：两类判断，不能混

| 类别 | 字段 | 判断依据 |
|---|---|---|
| **按应用类型裁剪** | `targetWordCount` `contentStructure` `visualStyle`（以及视频/音频/演示类的专有字段） | **响应里有没有这个 key** |
| **按当前取值联动** | `customTone` `customSections` `customFreshness` `customVisualStyle` | **当前枚举值是不是 `custom`** |

混为一谈会出两种 bug：

- 用后端不返回来判断 custom 字段 → 用户选了「自定义结构」却看不到填段落的地方
- 用"值是不是空"来判断类型裁剪 → 用户把字数填成 0 时，输入框自己消失

后端不返回某字段 = 这个应用类型没这个概念 = 不渲染。**不维护"哪个类型有哪些字段"的对照表**，
那种表和后端一旦不同步就是线上表单缺字段。

### 7.3 保存 与 保存并启用

顶部两个按钮，两条路径：

**【保存】** → `PUT`
- 成功 → 提示"已保存"，草稿仍是草稿
- 400 → 按 `field` 标红那一个输入框

**【保存并启用】** → `PUT` 然后 `POST .../ready`
- 都成功 → 提示"已就绪"，刷新（可能被自动选中，见 §5.3）
- `PUT` 成功但 `ready` 返回 422 → 遍历 `errors[]` 全部标红，跳到第一个出错的段

**最容易做错的地方**：`PUT` 成功、`ready` 失败时，**配置已经存进数据库了**，
只是没达到就绪标准。写成"整体失败"的话，用户以为白填了，退出去重填一遍。

正确的说法是 **「已保存，但还差这几项才能启用」**。

**不做自动保存。** 后端只有全量提交接口，自动保存 = 每敲几个字整包提交一次，
既浪费又容易和用户正在编辑的内容打架。

### 7.4 控件对照

| 字段 | 控件 |
|---|---|
| `maxSearchRounds` ∈{1,2,3} | Segmented 三格（同原型） |
| `allowedSources` / `excludedSources` | 标签输入（同原型） |
| `freshness` | 下拉；选「自定义」旁边展开天数输入 |
| `targetWordCount` | 下拉预设 + 「自定义」填数字 |
| `contentStructure` | 下拉 + 结构预览文案（前端硬编码）；选「自定义」变成**可拖拽排序**的段落列表 |
| `tone` / `visualStyle` | 下拉；选「自定义」展开文本框 |
| `sourceMode` | 大卡片单选三选一（借原型「系统推荐/自定义」那两张卡的样式） |
| `autoRevisionCount` ∈{0,1,2} | Segmented 三格 |

`customSections` 需要拖拽排序，因为**顺序就是正文段落的顺序**，有业务含义。

### 7.5 质量评审段

只剩 `autoRevisionCount` 一个控件。**保留这一段**，下面加只读说明：

> 🔒 评分维度、通过分数线、权重、硬性规则由平台统一管理，不开放修改——
> 保证不同客户的成品有一致的质量底线。

既诚实，又解释了这页为什么空，比直接删掉一整段体面。

## 8. 工程约定与环境隔离

**硬约束：本项目不得影响用户已配置好的公司开发环境。**

| 做法 | 不做 |
|---|---|
| 工具全进 `devDependencies` | 任何 `npm i -g` |
| 项目内 `.nvmrc` 指定 Node 版本 | 改 nvm 全局默认版本 |
| 依赖装在本项目 `node_modules` | 改 `~/.npmrc` / `~/.zshrc` |

开发时跨域用 **Vite dev server 代理**（`/v1` → `http://localhost:18080`），
不需要后端改任何东西。生产环境两条路：同域部署（nginx 反代），
或后端 `config.yaml` 的 `cors_origins` 填前端域名。

本地把后端跑起来：

```bash
cd ~/Work/wanyan/go/artifex-core
make migrate   # 首次，建表并种入 3 个图文模板
make run       # 监听 :18080
```

## 11. 枚举字典与演示数据兜底（2026-08-29 补）

### 11.1 枚举从后端来

后端补上了 `GET /v1/meta/enums`，返回 7 组共 37 个选项（`appType` / `recipeStatus` /
`sourceMode` / `freshness` / `contentStructure` / `tone` / `visualStyle`），
每项带 `value` + `label`，`appType` 额外带 `available`。

**这是枚举的唯一事实源。**页面一律通过 `useEnums()` 取，不再 import 本地字典渲染下拉框。
前端不维护"哪个枚举有哪些值"的对照表，后端新增枚举值页面自动跟上。

本地 `constants/enums.ts` 降级为两件事：

1. `FALLBACK_ENUMS` —— 首屏 meta 未返回、或后端没启动时的兜底，避免下拉框空白
2. 后端不提供的补充文案 —— 选项说明（`SOURCE_MODE_DESC`）、结构预览（`CONTENT_STRUCTURE_PREVIEW`）、
   类型副标题（`APP_TYPE_DESC`）

`useEnums().label()` 遇到字典里没有的值，回退显示原值——不崩，也让不同步看得见。

### 11.2 后端没启动时用演示数据

`src/mocks/` 提供一份内存版后端。触发条件：`fetch` 抛异常，或 Vite 代理回
502/503/504（后端没起时代理就是回这个）。

三条设计取舍：

- **每次都先真调，失败才回落。** 不做"一旦离线就永久走 mock"，
  这样后端启动后能自动切回真实数据，用户不用刷新页面。代价是后端没起时
  每个请求多一次本地往返（约 1ms）。
- **只在开发环境启用**，且可用 `VITE_DISABLE_MOCK=1` 关掉。
  **线上绝不能出现假数据。**`mocks/server.ts` 必须用**动态 import**——
  它在模块顶层初始化演示数据，属于模块副作用，静态 import 时打包器无法摇除，
  演示数据会进入生产产物。CI 已加 grep 产物的卡点；本地改动后同样应
  `pnpm build` 后复查一次。
- **必须有显眼横幅**（`OfflineBanner`）。看着真数据其实是假数据，
  比页面直接报错危险得多。

mock 模拟的是接口的**形状和关键行为**，不是完整后端：应用列表扁平、
系统配方不返回 `appType`、保存只过格式校验（400 单字段）、
转就绪查必填项（422 一次给全部）、只有就绪配方能被选中（409）。

**刻意不做**的：软删、事务、跨类型校验、重名判重的完整规则。
要验证这些必须连真后端。

演示数据里有一份 `待补全的测试配方`（草稿，缺目标受众与创作目标），
点「保存并启用」可稳定复现 422 批量标红。

### 11.4 自定义段落的拖拽排序

`contentStructure = custom` 时的段落列表用 `SortableTextList`（dnd-kit），
**从上到下就是正文段落的顺序**。原来用标签输入做不到调序——只能删了重加。

条目值本身当拖拽 id，因此**不允许重名**（段落名重复本来也没意义）。
这比维护一套并行的 id 简单，代价是加重名时要给提示。
