# artifex-web 部署与发版

> 与后端 `artifex-core` 的流程完全一致：**打个版本 tag → 自动上线**。
> 前后端各自独立发版，改前端不用重启后端，反之亦然。

---

## 0 · 怎么发版

**合并到 `main` 就自动上线**：

- 开 PR → 自动跑检查（类型、lint、测试、构建），不过不让合；
- 合并进 `main` → 再跑一遍检查 → 构建镜像 → 推 ghcr → SSH 到服务器拉新镜像重启 → 确认首页 200；
- 想留正式版本号时打 tag（`git tag v0.2.0 && git push origin v0.2.0`），同样上线，并留下 `:v0.2.0` 镜像方便回退。版本号用语义化 `v主.次.补丁`。

  **`0.x` 阶段**（当前）：产品未正式发布，接口与页面都可能变。
  `v0.0.1` 首次上线 · `v0.1.0` 加了成块的功能 · `v0.0.2` 修 bug。

  等产品对外正式发布、接口稳定下来，再进 `v1.0.0`。主版本号是给使用者的
  承诺——`1.x` 意味着不会再随意改破坏性的东西，不到那一步别用。

## 一、部署形态：同域，nginx 统一入口

```
用户 ──> 服务器 nginx（80/443，一个域名）
           │
           └──> 前端容器 127.0.0.1:18082
                  ├─ /       静态文件（dist）
                  └─ /v1/*   反代到后端容器 artifex-app:8080
                                    │
                                    └──> MySQL
```

**为什么同域**：浏览器眼里前后端是同一个站，**跨域问题直接不存在**。
生产构建的 `VITE_API_BASE` 留空（见 `.env.production`），前端走相对路径 `/v1`，
后端也不用维护 CORS 白名单——那玩意漏配一个端口就联调不通。
一个域名、一张证书。

**只暴露前端一个入口**。后端容器始终只绑 `127.0.0.1:18080`，不对外；
`/v1` 由前端容器内的 nginx 转过去。

## 二、四个文件各管什么

| 文件 | 管什么 |
|---|---|
| `deployments/Dockerfile` | 两阶段构建：Node 层跑 `pnpm build`，产物拷进 nginx 层。**最终镜像里没有 Node、没有 node_modules**，约 78 MB |
| `deployments/nginx.conf` | **容器内**的 nginx：静态托管 + SPA 回退 + `/v1` 反代 + 缓存头 |
| `deployments/docker-compose.server.yaml` | 服务器上怎么跑这个容器。发版时流水线同步到 `/opt/artifex/docker-compose.web.yaml` |
| `deployments/nginx-host.conf.example` | **服务器上**那台 nginx 的 server 块示例，反代到前端容器 |

### nginx.conf 里三条不能删的

**SPA 路由回退**——`/apps/xxx/recipes` 这种路径磁盘上没有对应文件，
不配 `try_files ... /index.html` 的话，用户刷新页面直接 404。

**index.html 绝不缓存**——否则发版后用户拿到旧 HTML，
里面引用的是已经不存在的旧 assets 文件名，**页面白屏**。
带哈希的 assets 反过来可以长缓存，文件名变了自然就换了。

**proxy_read_timeout 300s**——生产任务这类接口可能跑很久，默认 60s 会被掐断。

## 三、首次部署要做的

前三步只做一次。

### 1. GitHub 仓库 Secrets

`Settings → Secrets and variables → Actions`，加四个：

| 名字 | 是什么 |
|---|---|
| `SERVER_HOST` | 服务器 IP |
| `SERVER_USER` | 登录用户名 |
| `SERVER_PASSWORD` | 登录密码 |
| `GHCR_TOKEN` | Personal Access Token（classic），拉私有镜像用 |

> `GITHUB_TOKEN` 不用配，GitHub 自动提供（用于推镜像到 ghcr）。

`GHCR_TOKEN` 有两个容易漏的点，缺任一都会「login 成功但 pull 被拒」：

1. 勾上 **`read:packages`** 权限
2. 组织的包还需对该组织做 **SSO 授权**——token 列表里点 `Configure SSO`
   → 找到 `NinePhoenixs` → `Authorize`

### 1.1 凭据必须按项目隔离

`docker login` 的凭据默认是**机器级**的：`/root/.docker/config.json` 里
每个 registry 只有一个槽位。服务器同时跑着前端和后端，两边各自
`docker login` 会互相覆盖——**谁后发版谁把对方的凭据顶掉**，于是两个项目
都拉不动镜像。GitHub 上仓库是隔离的，服务器上不是。

解法是在部署脚本里用 `DOCKER_CONFIG` 指定各自的凭据目录：

| 项目 | 凭据目录 |
|---|---|
| artifex-web | `/opt/artifex/.docker-web` |
| artifex-core | `/opt/artifex/.docker-core` |

> 另一种解法是把 ghcr 镜像设为 Public，就完全不需要凭据。
> 但 `NinePhoenixs` 组织策略当前禁用了公开包
> （`Settings → Packages → Package creation` 里可放开）。

### 2. 服务器准备

和后端共用 `/opt/artifex`，按后端仓库 `docs/部署发版指南.md`「新服务器从零准备」做一次即可
（装 Docker、放 `.env` 和 `config.local.yaml`）。前端自己不需要额外文件：
compose 由流水线同步，`artifex` 网络由流水线创建，前后端谁先发版都行。

### 3. 服务器 nginx 加一个 server 块

照 `deployments/nginx-host.conf.example` 改好域名，放到 nginx 的站点配置目录
（如 `/etc/nginx/conf.d/artifex.conf`；用面板管理 nginx 的，在面板里加一个反向代理站点，
目标 `http://127.0.0.1:18082`），然后 `nginx -t && nginx -s reload`。

- 只暴露这一个入口：`/v1` 由前端容器内的 nginx 反代到后端；
- 云厂商安全组放行 80 / 443；
- 有域名后用 `certbot --nginx -d 你的域名` 签 HTTPS。

## 四、验证与回退

### 确认线上是哪个版本

```bash
docker inspect artifex-web --format '{{.Config.Image}}'
docker compose -f docker-compose.web.yaml images
```

### 回退

每个版本的镜像都带版本号永久留在 ghcr。服务器 `/opt/artifex/.env` 里加一行
`WEB_TAG=v0.0.1`，再 `docker compose -f docker-compose.web.yaml up -d`；恢复最新删掉这行即可。

## 五、本地验证镜像

发版前想先在本地确认镜像没问题：

```bash
docker build -f deployments/Dockerfile -t artifex-web:test .
docker run -d --name artifex-web-test -p 18082:80 artifex-web:test
curl -o /dev/null -w '%{http_code}\n' http://localhost:18082/
```

**国内网络拉不动 Docker Hub 时**，先用镜像源拉基础镜像再打标准标签
（Dockerfile 本身保持标准写法，CI 上是直连的）：

```bash
for i in node:22-alpine nginx:1.27-alpine; do
  docker pull docker.m.daocloud.io/library/$i && docker tag docker.m.daocloud.io/library/$i $i
done
```

**本地测 `/v1` 反代要注意**：`nginx.conf` 里的 `artifex-app:8080` 是
**生产环境后端容器内**的地址。本地后端如果是宿主机裸进程（监听 18080），
容器访问不到，会返回 502——这不是配置错，是环境不同。本地想验反代，
临时把 upstream 换成 `host.docker.internal:18080`：

```bash
sed 's|server artifex-app:8080;|server host.docker.internal:18080;|' \
  deployments/nginx.conf > /tmp/nginx-localtest.conf
docker run -d --name artifex-web-test -p 18082:80 \
  -v /tmp/nginx-localtest.conf:/etc/nginx/conf.d/default.conf:ro artifex-web:test
```

应验证的四项：首页可访问、SPA 路由回退生效、`/v1/apps` 与 `/v1/meta/enums` 可通、
静态资源为 `Cache-Control: public, immutable` 且 `index.html` 为 `no-store`。

## 六、CI 会拦什么

每次推送和 PR 跑 `.github/workflows/ci.yml`：类型检查 → 测试 → 构建 →
**检查演示数据没混进生产产物**。

最后一条是硬性卡点：`src/mocks/` 必须用动态 `import()` 才会被摇除。
改成静态 import 会导致演示数据进入生产产物，CI 直接 grep 产物拦截。

## 附：与后端的对应关系

| | artifex-core（后端） | artifex-web（前端） |
|---|---|---|
| 镜像 | `ghcr.io/ninephoenixs/artifex-core` | `ghcr.io/ninephoenixs/artifex-web` |
| compose | `/opt/artifex/docker-compose.core.yaml`（含 MySQL） | `/opt/artifex/docker-compose.web.yaml` |
| 端口 | `127.0.0.1:18080` → 容器 8080 | `127.0.0.1:18082` → 容器 80 |
| 对外 | 不暴露 | 服务器 nginx 反代过来 |
| 发版 | 打 tag | 打 tag（各自独立） |
