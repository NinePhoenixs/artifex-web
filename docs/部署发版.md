# artifex-web 部署与发版

> 与后端 `artifex-core` 的流程完全一致：**打个版本 tag → 自动上线**。
> 前后端各自独立发版，改前端不用重启后端，反之亦然。

---

## 0 · 怎么发版

```bash
git tag v0.0.1
git push origin v0.0.1     # ← 打 tag 才触发发版
```

剩下全自动：构建镜像 → 推 ghcr → SSH 到服务器 → 拉新镜像重启。

- **日常开发不发版**：改代码 → PR → 合并 `main`（只攒代码、跑检查，不上线）
- **要发布时**才打 tag。版本号用语义化 `v主.次.补丁`。

  **`0.x` 阶段**（当前）：产品未正式发布，接口与页面都可能变。
  `v0.0.1` 首次上线 · `v0.1.0` 加了成块的功能 · `v0.0.2` 修 bug。

  等产品对外正式发布、接口稳定下来，再进 `v1.0.0`。主版本号是给使用者的
  承诺——`1.x` 意味着不会再随意改破坏性的东西，不到那一步别用。

## 一、部署形态：同域，nginx 统一入口

```
用户 ──> 服务器 nginx（80/443，一个域名）
           │
           └──> 前端容器 127.0.0.1:18082
                  ├─ /       静态文件（dist）
                  └─ /v1/*   反代到后端容器 artifex-app:8080
                                    │
                                    └──> MySQL
```

**为什么同域**：浏览器眼里前后端是同一个站，**跨域问题直接不存在**。
生产构建的 `VITE_API_BASE` 留空（见 `.env.production`），前端走相对路径 `/v1`，
后端也不用维护 CORS 白名单——那玩意漏配一个端口就联调不通。
一个域名、一张证书。

**只暴露前端一个入口**。后端容器始终只绑 `127.0.0.1:18080`，不对外；
`/v1` 由前端容器内的 nginx 转过去。

## 二、四个文件各管什么

| 文件 | 管什么 |
|---|---|
| `deployments/Dockerfile` | 两阶段构建：Node 层跑 `pnpm build`，产物拷进 nginx 层。**最终镜像里没有 Node、没有 node_modules**，约 78 MB |
| `deployments/nginx.conf` | **容器内**的 nginx：静态托管 + SPA 回退 + `/v1` 反代 + 缓存头 |
| `deployments/docker-compose.server.yaml` | 服务器上怎么跑这个容器。放到 `/opt/artifex/docker-compose.web.yaml` |
| `deployments/nginx-host.conf.example` | **服务器上**那台 nginx 的 server 块示例。该服务器用宝塔面板，配置目录是 `/www/server/panel/vhost/nginx/`，且已有多个站点，**只加不改** |

### nginx.conf 里三条不能删的

**SPA 路由回退**——`/apps/xxx/recipes` 这种路径磁盘上没有对应文件，
不配 `try_files ... /index.html` 的话，用户刷新页面直接 404。

**index.html 绝不缓存**——否则发版后用户拿到旧 HTML，
里面引用的是已经不存在的旧 assets 文件名，**页面白屏**。
带哈希的 assets 反过来可以长缓存，文件名变了自然就换了。

**proxy_read_timeout 300s**——生产任务这类接口可能跑很久，默认 60s 会被掐断。

## 三、首次部署要做的

前三步只做一次。

### 1. GitHub 仓库 Secrets

`Settings → Secrets and variables → Actions`，加三个：

| 名字 | 是什么 |
|---|---|
| `SERVER_HOST` | 服务器 IP |
| `SERVER_USER` | 登录用户名 |
| `SERVER_PASSWORD` | 登录密码 |

> `GITHUB_TOKEN` 不用配，GitHub 自动提供（用于推镜像到 ghcr）。
>
> **不需要 `GHCR_TOKEN`**——ghcr 上的镜像设为公开，服务器匿名即可拉取。
> 原因见下方「为什么镜像设为公开」。

### 1.1 把镜像设为公开（只做一次）

首次发版把镜像推上去之后，到
`https://github.com/orgs/NinePhoenixs/packages` 找到 `artifex-web` →
`Package settings` → 最下方 `Change visibility` → 选 `Public`。

**为什么镜像设为公开**

`docker login` 的凭据是**机器级**的：`/root/.docker/config.json` 里每个
registry 只有一个槽位。这台服务器同时跑着多个项目，各项目在部署脚本里
各自 `docker login`，**谁后发版谁把别人的凭据顶掉**。GitHub 上两个仓库是
隔离的，服务器上不是。

镜像公开后不需要任何凭据，这类冲突从根上消失，也不必维护会过期的 token。

安全上没有额外暴露：仓库本身已是公开的，镜像里装的就是这些源码的构建
产物；真正的密钥在 `config.local.yaml`，运行时从服务器挂载，不进镜像。

### 2. 服务器上放 compose 文件

```bash
scp deployments/docker-compose.server.yaml 用户@服务器:/opt/artifex/docker-compose.web.yaml
```

**注意确认网络名**。前端容器必须和后端容器在同一个 docker 网络，
容器内的 nginx 才能用容器名 `artifex-app` 找到后端：

```bash
docker inspect artifex-app --format '{{json .NetworkSettings.Networks}}' | python3 -m json.tool
```

把查到的网络名填进 compose 的 `networks.blognet.name`。当前值
`wunderminibar_blog_default` 已在服务器上核对过，与后端一致。

**端口 18082 也已核对**：18080 被后端占用，18081 被 `sporttery-data-console`
占用，18082 空闲。换服务器时需重新确认。

### 3. 服务器 nginx 加一个 server 块

> **本项目已完成**：配置在 `/www/server/panel/vhost/nginx/artifex-web.conf`，
> 监听 18090 转发到 `127.0.0.1:18082`。删除该文件并 `nginx -s reload` 即可回滚。
>
> 无域名期间用 `http://39.106.129.214:18090` 访问，**需在阿里云安全组放行 18090**。
> 已放行的端口：80 / 443 / 18080 / 18081。
>
> 拿到域名后把 `listen 18090` 改成 `listen 80` 并填 `server_name`，
> 80 端口已放行，无需再动安全组。注意 `server_name 39.106.129.214` 在 80 端口
> 已被 `lottery-recognition` 占用，必须用域名而非 IP。


该服务器使用**宝塔面板**，nginx 配置在 `/www/server/panel/vhost/nginx/`，
不是 `/etc/nginx/conf.d/`。机器上已有 `www.wunderminibar.com` 等站点，**只加不改**。

两种方式，任选：

- **面板操作**：网站 → 添加站点 → 反向代理，目标 `http://127.0.0.1:18082`
- **手动**：照 `deployments/nginx-host.conf.example` 改好域名，放到
  `/www/server/panel/vhost/nginx/artifex-web.conf`，然后 `nginx -t && nginx -s reload`

HTTPS 在面板里申请 Let's Encrypt 证书最省事（网站 → SSL）。

## 四、验证与回退

### 确认线上是哪个版本

```bash
docker inspect artifex-web --format '{{.Config.Image}}'
docker compose -f docker-compose.web.yaml images
```

### 回退

每个版本的镜像都带版本号永久留在 ghcr。把 compose 里的 `:latest`
改成要回退的 tag（如 `:v0.0.1`），再 `up -d` 即可。

## 五、本地验证镜像

发版前想先在本地确认镜像没问题：

```bash
docker build -f deployments/Dockerfile -t artifex-web:test .
docker run -d --name artifex-web-test -p 18082:80 artifex-web:test
curl -o /dev/null -w '%{http_code}\n' http://localhost:18082/
```

**国内网络拉不动 Docker Hub 时**，先用镜像源拉基础镜像再打标准标签
（Dockerfile 本身保持标准写法，CI 上是直连的）：

```bash
for i in node:22-alpine nginx:1.27-alpine; do
  docker pull docker.m.daocloud.io/library/$i && docker tag docker.m.daocloud.io/library/$i $i
done
```

**本地测 `/v1` 反代要注意**：`nginx.conf` 里的 `artifex-app:8080` 是
**生产环境后端容器内**的地址。本地后端如果是宿主机裸进程（监听 18080），
容器访问不到，会返回 502——这不是配置错，是环境不同。本地想验反代，
临时把 upstream 换成 `host.docker.internal:18080`：

```bash
sed 's|server artifex-app:8080;|server host.docker.internal:18080;|' \
  deployments/nginx.conf > /tmp/nginx-localtest.conf
docker run -d --name artifex-web-test -p 18082:80 \
  -v /tmp/nginx-localtest.conf:/etc/nginx/conf.d/default.conf:ro artifex-web:test
```

应验证的四项：首页可访问、SPA 路由回退生效、`/v1/apps` 与 `/v1/meta/enums` 可通、
静态资源为 `Cache-Control: public, immutable` 且 `index.html` 为 `no-store`。

## 六、CI 会拦什么

每次推送和 PR 跑 `.github/workflows/ci.yml`：类型检查 → 测试 → 构建 →
**检查演示数据没混进生产产物**。

最后一条是硬性卡点：`src/mocks/` 必须用动态 `import()` 才会被摇除。
改成静态 import 会导致演示数据进入生产产物，CI 直接 grep 产物拦截。

## 附：与后端的对应关系

| | artifex-core（后端） | artifex-web（前端） |
|---|---|---|
| 镜像 | `ghcr.io/ninephoenixs/artifex-core` | `ghcr.io/ninephoenixs/artifex-web` |
| compose | `/opt/artifex/docker-compose.server.yaml` | `/opt/artifex/docker-compose.web.yaml` |
| 端口 | `127.0.0.1:18080` → 容器 8080 | `127.0.0.1:18082` → 容器 80 |
| 对外 | 不暴露 | 服务器 nginx 反代过来 |
| 发版 | 打 tag | 打 tag（各自独立） |
